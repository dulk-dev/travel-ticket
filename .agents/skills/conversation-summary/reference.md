## 阶段记录模板

用于记录大方向讨论（需求分析、技术选型、交互设计等）。

```markdown
# 需求分析：旅行票务系统的核心功能定义

**日期**: 2025-07-10
**阶段**: 需求分析
**输入**: 用户发送了一张手绘原型图，描述了旅行票务系统的基本流程

---

## 背景

用户希望开发一个旅行票务系统，核心需求是让用户能够搜索、预订和管理旅行票据（机票、火车票、酒店等）。用户通过一张手绘原型图表达了初步想法，需要我们一起梳理和细化需求。

---

## 讨论过程

### 1. 核心用户场景识别

**问题**：这个系统主要服务谁？解决什么痛点？

**讨论**：
- 目标用户：个人旅行者，而非企业差旅
- 核心痛点：现有平台信息分散，用户需要在多个 App 间切换比价
- 差异化方向：聚合多类票务，提供一站式行程管理

**决策**：聚焦个人旅行者的"行程规划 + 票务预订"一体化体验

---

### 2. 功能范围界定

**问题**：MVP 应该包含哪些功能？哪些可以后续迭代？

**讨论**：
- 必须有的：搜索、预订、订单管理、支付
- 可以后续加的：智能推荐、价格预测、社交分享
- 争议点：是否需要实时库存同步？

**决策**：
- MVP 包含：搜索（机票+酒店）、预订流程、订单列表、基础支付
- 第一版采用"查询后跳转供应商"模式，暂不实现实时库存
- 后续迭代再考虑直连供应商 API

---

### 3. 技术架构初步方向

**问题**：前端用什么框架？后端如何处理多供应商对接？

**讨论**：
- 前端：React vs Vue vs Next.js
- 后端：是否需要独立后端？还是先纯前端 demo？

**决策**：
- 前端使用 Next.js（SSR 有利于 SEO，且内置 API Route 可模拟后端）
- 第一阶段用 Mock 数据 + API Route 模拟供应商接口
- 后续再引入真实后端服务

---

## 关键思路

- **聚合优于自建**：与其自己维护库存，不如做信息聚合层，降低初期复杂度
- **渐进式扩展**：从单一票务类型（机票）开始，验证模式后再扩展
- **SEO 优先**：旅行类搜索流量大，SSR 对初期获客很重要

---

## 待确认事项

- [ ] 酒店预订是否纳入 MVP？还是仅机票？
- [ ] 支付流程用真实接口还是模拟？
- [ ] 用户体系是否需要注册登录？还是游客模式先跑通？

## 需求描述

根据需求分析阶段的决策，需要实现机票搜索的核心页面：
- 展示搜索结果列表（航班信息、价格、时间）
- 支持按价格、时间排序
- 支持按航司、舱位筛选
- 响应式布局，适配移动端

---

## 实现过程

### 1. 组件拆分思路

将页面拆分为：
- `FlightSearchPage`：页面级组件，管理状态和 URL 参数
- `SearchFilter`：筛选栏，管理筛选条件
- `FlightCard`：单个航班卡片，展示航班信息
- `SortBar`：排序栏，切换排序方式

### 2. 状态管理

使用 URL 参数作为状态来源（便于分享和刷新保持）：
- `?from=PEK&to=SHA&date=2025-08-01&sort=price&airline=CA`
- 筛选变化时更新 URL，页面从 URL 解析状态

### 3. 关键实现

**FlightCard 组件**：

```tsx
// 展示航班核心信息，支持展开详情
export function FlightCard({ flight }: { flight: Flight }) {
  const [expanded, setExpanded] = useState(false)
  
  return (
    <Card>
      <CardHeader>
        <AirlineLogo code={flight.airline} />
        <FlightTime 
          departure={flight.departure} 
          arrival={flight.arrival} 
        />
        <PriceTag amount={flight.price} />
      </CardHeader>
      {expanded && <FlightDetail flight={flight} />}
    </Card>
  )
}
```

**URL 状态同步**：

```tsx

## 遇到的问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 筛选条件过多时 URL 过长 | 每个筛选都作为独立参数 | 使用 nuqs 的解析器，将对象序列化为紧凑格式 |
| 移动端筛选栏占用过多空间 | 侧边栏在移动端展示不佳 | 改为底部抽屉式筛选，点击后从底部弹出 |
| 航班时间跨天显示混乱 | 到达时间可能为次日 | 添加"+1 天"标识，并显示完整日期 |

## 编写规范

### 阶段记录

#### 阶段名称

- 使用"方向 + 具体内容"的格式
- 示例："需求分析：旅行票务系统的核心功能定义"、"技术选型：前端框架与状态管理方案"

#### 背景

- 1-2 句话说明本次讨论的起点
- 说明用户提供了什么输入（图片、想法、问题）

#### 讨论过程

- 每个讨论点使用独立的二级标题
- 结构：**问题 → 讨论 → 决策**
- 讨论部分记录我们考虑了哪些选项，各自的优劣
- 决策部分明确最终选择及理由

#### 关键思路

- 记录讨论中产生的有价值的洞察
- 不一定形成了最终决策，但对理解项目方向有帮助
- 用简洁的语言描述，便于后来者快速理解

#### 待确认事项

- 使用任务列表格式（`- [ ]`）
- 记录讨论中提出但尚未确定的事项
- 这些事项可能影响后续开发

### 执行记录

#### 目标

- 一句话说明本次要解决什么问题或实现什么功能
- 示例："实现机票搜索结果的列表展示，支持基础筛选和排序"

#### 需求描述

- 简要描述需求来源和具体内容
- 可以引用阶段记录中的决策

#### 实现过程

- 记录从需求到代码的思考路径
- 包含：拆分思路、状态设计、关键实现
- 关键代码片段控制在 5-15 行

#### 遇到的问题

- 使用三列表格：问题 | 原因 | 解决方案
- 每个问题一行，简洁描述

#### 文件变更

- 使用相对于项目根目录的路径
- 变更类型：新增 / 修改 / 删除
- 说明控制在 10 个字以内
